# Lessons from related projects

We read real failure reports and proposals in related open-source projects to choose small, testable improvements for Jarvis. These projects serve different purposes. Their popularity and historical issues are not a benchmark, and nothing here claims Jarvis is better than them. Each status below is what we saw at inspection time (November 2026); it does not describe their current versions. An open or historical report is not evidence of an unfixed problem today, and an unmerged proposal has not shipped.

| Primary discussion (status at inspection) | Practical lesson | What Jarvis does |
| --- | --- | --- |
| [Handy #2268](https://github.com/cjpais/Handy/issues/2268), open; proposed fix [#2290](https://github.com/cjpais/Handy/pull/2290), open and unmerged | A successful HTTP response is not proof of useful output. Keep the user's input and show an explicit failure. | The provider boundary already rejects blank or whitespace-only replies and returns a fixed error message instead. The local dashboard works without any AI provider. This guard predates this review; it was not invented in response to it. |
| [Open Interpreter #1741](https://github.com/openinterpreter/openinterpreter/pull/1741), closed and unmerged; [#393](https://github.com/openinterpreter/openinterpreter/issues/393), closed as not planned | A plan, or an attempted action, is not completed execution. Permission and outcome need separate states. | Fixed commands; actions armed separately on this computer; AI replies are plain text and cannot act. Start observing never arms an action. "Stop confirmed" appears only when Jarvis answers that Stop with a fully stopped state; otherwise the dashboard says Stop was not confirmed. A successful Windows lock request is described as a request, not a verified lock. |
| [Leon #480](https://github.com/leon-ai/leon/issues/480), open; [maintainer's request for a diagnostic report](https://github.com/leon-ai/leon/issues/480#issuecomment-1525565166) | Reproducible diagnostics beat trial-and-error installation advice. | **Copy diagnostics** reports mode, operating system, Python version, optional package and model availability, connection state and a fixed failure category. It never includes keys, chat text, file paths, host names or camera data. Installers keep their fixed-argument boundaries; no shell commands are suggested. |
| [Home Assistant #176843](https://github.com/home-assistant/core/pull/176843), draft and unmerged, with reviewer disagreement about presenting transient unavailability as a repair | A transient connection loss differs from a fixable configuration problem, and "unavailable" differs from "absent". | The dashboard has distinct connecting, live, delayed, lost and restarted states. Freshness is measured with a monotonic clock. Readings become unknown rather than zero. Before the first status nothing claims standby, disarmed or demo. Stop stays available as an attempt. A lost connection is never reported as a stopped guard. |

The dashboard behavior above is covered by `tests/browser_dashboard.cjs`, which `node tests/browser_quickstart.cjs` runs with a mocked local API and no real devices. Simulated tests are not evidence of camera accuracy or of a completed operating-system lock; see [Limits worth understanding](../README.md#limits-worth-understanding).
